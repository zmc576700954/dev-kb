# 知识库写作与管理规范（Agent 执行版）

> 本文件面向执行知识库整理、写作、搬迁、索引维护的自动化 Agent。
> 每条规则都是**可机械判定**的：给定文件内容，能直接得出「合规 / 不合规」。
> 规则只用「必须 / 建议 / 禁止」三档，不设中间态。

---

## 0. 使用方式与约定

### 0.1 规则强度

| 标记 | 含义 | Agent 的行为 |
|---|---|---|
| **必须** | 硬性要求 | 不满足就不交付；已存在的不合规内容要修到合规 |
| **建议** | 默认做法 | 除非有明确理由，否则照做；偏离时不报错 |
| **禁止** | 硬性禁止 | 出现即视为缺陷，必须消除 |

冲突处理顺序：**禁止 > 必须 > 建议**。两条同等强度的规则冲突时，取更严格的一条执行，并在交付说明里记录冲突点与取舍。

### 0.2 占位符

| 占位符 | 指代 |
|---|---|
| `<project>/` | 一个知识库项目的根目录 |
| `<category>/` | 项目内的一级分类目录 |
| `<doc>.md` | 一篇文档 |
| `<asset>` | 图片或附件文件名 |
| `<NN>` | 两位数字序号，如 `01`、`02` |

除占位符外，本文不引用任何具体项目名、目录名或文件名。

### 0.3 判定原则

- 一条规则只说一种要求；出现「视情况」「酌情」「尽量」即视为本文缺陷，按最严格解释执行。
- 「存在」指**路径逐字符相同**且大小写一致；`Foo.md` 与 `foo.md` 是两个文件。
- 所有文本判定基于 UTF-8 解码后的内容；无法按 UTF-8 解码的文件按「必须」级缺陷上报，不做静默跳过。

## 1. 目录层级与职责

知识库的固定形状：

```
<project>/
├── README.md                 ← 项目索引，唯一入口
├── <category>/
│   ├── <NN>-<doc>.md
│   └── <doc>.md
└── assets/                   ← 可选：项目级图片与附件
```

| 层级 | 职责 | 规则 |
|---|---|---|
| `<project>/` | 一个独立主题域，内部自洽、可单独阅读 | **必须**：一级目录即项目，不再嵌套第二层项目目录 |
| `<category>/` | 一个子主题，承载 3–15 篇文档 | **必须**：分类只放同级主题；跨主题内容另建分类 |
| `<doc>.md` | 一篇只讲一件事的文档 | **必须**：一个文件只对应一个主主题 |
| `README.md` | 索引与入口 | **必须**：每个项目根恰好一个，见第 2 节 |
| `assets/` | 图片、附件 | **建议**：统一放项目级 `assets/`，不散落在分类目录里 |

补充硬性规则：

- **必须**：项目根只允许出现 `README.md` 一个 Markdown 文件；其余文档一律落在某个分类目录下。
- **必须**：每个项目至少有一个分类目录。
- **禁止**：出现空的分类目录（目录下没有任何文档）。
- **禁止**：文档直接放在项目根（`README.md` 除外）。
- **禁止**：分类目录下再建子分类目录；层级最深到「项目 / 分类 / 文档」。
- **建议**：分类目录内的文档数量控制在 3–15 篇；超过 15 篇按主题拆分为两个分类。

## 2. README 索引

`README.md` 是读者和 Agent 的**唯一入口**，不是欢迎页。

### 2.1 必备内容（顺序固定）

1. **必须**：一级标题（`# `），内容为项目名称。
2. **必须**：紧跟一段 `> ` 引用块，一句话说明该项目解决什么问题、覆盖范围是什么。
3. **必须**：按分类分组的链接清单，每个分类一个小标题（`## `），下面用无序列表列出该分类全部文档。
4. **必须**：每个文档链接写成 `- [文档标题](./<category>/<doc>.md) — 一句话说明`。
5. **建议**：可选的「阅读路径」小节，按入门到进阶排序；阅读路径与文档状态、优先级无关，不要混用。

### 2.2 硬性规则

- **必须**：README 的链接覆盖项目内**全部**文档，不漏任何一篇。
- **必须**：新增、改名、移动、删除文档时，同一次变更内同步更新 README 链接。
- **必须**：README 中的链接目标实际存在；断链数为 0。
- **禁止**：README 中链接到不存在或已归档但未标注的文档。
- **禁止**：在 README 中堆叠正文内容；README 只做导航，正文留在文档里。
- **禁止**：README 使用 frontmatter（见 3.1）。
- **建议**：README 长度控制在 150 行以内；超过说明分类过粗或文档说明过长。

### 2.3 判定方法

对项目内所有 `.md`（README 除外）逐一检查：能否从 `README.md` 出发，沿相对链接走到该文件。存在走不到的文档，即为「必须」级缺陷。

## 3. frontmatter 与元数据

### 3.1 是否需要

| 文件 | frontmatter |
|---|---|
| 普通文档 `<doc>.md` | **必须**有，且位于文件第一行 |
| `README.md` | **禁止**有 |

### 3.2 格式

- **必须**：第一行是 `---`，最后一行是 `---`，两者之间每行一个 `键: 值`。
- **必须**：键与值之间恰好一个半角冒号加一个空格（`: `）。
- **必须**：只允许**单层扁平标量**；值可以是任意文本、日期、枚举。
- **禁止**：嵌套结构、列表、多行值、YAML 锚点与引用。
- **禁止**：空 frontmatter 块（`---` 之间没有任何 `键: 值` 行）。
- **禁止**：在 frontmatter 中出现正文内容。

模板：

```markdown
---
优先级: 高
状态: 稳定
最后更新: 2026-01-15
下次复核: 2026-07-15
---

# 文档标题

> 一句话说清这篇文档讲什么。

正文……
```

### 3.3 必填键

| 键 | 取值 | 缺失时 |
|---|---|---|
| `状态` | `草案` / `稳定` / `需监控` / `已废弃` / `已归档` | **必须**补齐，取最保守值 `草案` |
| `最后更新` | `YYYY-MM-DD` | **必须**补齐，取该文档最近一次实质修改日期 |
| `下次复核` | `YYYY-MM-DD` 或 `按需` | **必须**补齐；无法确定日期时填 `按需` |

### 3.4 可选键

| 键 | 取值 | 说明 |
|---|---|---|
| `优先级` | `高` / `中` / `低` | 缺省视为 `中`；只表示重要性，不表示阅读顺序 |
| `标签` | 逗号分隔的小写词，每个不超过 12 个字符，总数不超过 5 个 | 用于检索；不写同义词堆叠 |

### 3.5 取值规则

- **必须**：`状态` 只能取 3.3 表中的五个基准值之一；补充说明写在基准值之后，用全角括号包裹，如 `稳定（价格按季度复核）`。
- **必须**：`最后更新` 与 `下次复核` 的日期严格使用 `YYYY-MM-DD`，月、日补零。
- **必须**：`下次复核` 不早于 `最后更新`。
- **必须**：`最后更新` 表示「该条目的登记或复核日期」，不是「文件系统最后修改时间」；搬运或格式化导致的内容变化不得刷新该字段。
- **禁止**：同一文档出现重复键。
- **建议**：`下次复核` 按内容稳定性设定：法规、价格、外部依赖类 3 个月，方法论类 6 个月，历史记录类填 `按需`。

## 4. 文件与目录命名

### 4.1 允许字符

- **必须**：路径（各级目录名与文件名）只能包含：中文、英文字母、数字、连字符 `-`、点 `.`、斜杠 `/`。
- **禁止**：空格、制表符、下划线 `_`、半角括号 `()`、全角括号 `（）`、方括号 `[]`、方头括号 `【】`、`#`、`&`、`%`、`+`、`=`、`;`、`,`、`'`、`"`、`!`、`?`、`*`、`|`、`<`、`>`。
- **禁止**：以 `.` 或 `~` 开头的文件与目录（临时文件、备份文件）。
- **禁止**：以 `_` 开头的一级目录参与正式内容；此类目录视为内部目录，不进入索引、不进入检索结果、不被 README 链接。

### 4.2 命名形状

- **建议**：分类目录使用 `<NN>-<分类名>/`，编号从 `01` 起，允许不连续。
- **建议**：文档使用 `<NN>-<标题>.md`，同一分类内编号唯一；不要求连续。
- **必须**：同一目录下的文件名互不相同，且区别不能只靠大小写。
- **必须**：文件名主体长度不超过 60 个字符（不含扩展名与 `/`）。
- **禁止**：文件名使用版本后缀（`-v2`、`-最终版`、`-new`）；版本通过文档状态与正文变更说明表达。
- **禁止**：文件名使用「未命名」「新建文档」「副本」「copy」等无信息词。
- **建议**：文件名中的英文统一小写；中文名不夹杂拼音。专有名词、缩写与品牌名（`ComfyUI`、`SDXL`、`TTS` 等）保留原文大小写。

### 4.3 路径安全

- **禁止**：路径中出现 `..` 或指向项目根之外。
- **禁止**：绝对路径作为文档标识。
- **禁止**：符号链接指向项目根之外的目标。
- **必须**：移动文档时保留原分类语义；跨分类移动视为主题变更，需同步更新 README 与该文档的全部入链。

## 5. 标题层级与正文骨架

### 5.1 标题

- **必须**：每篇文档恰好一个一级标题（`# `），且位于 frontmatter 之后、正文最前。
- **必须**：标题层级连续，不跳级（出现 `###` 前必须有 `##`）。
- **必须**：同级标题之间必须有正文；**禁止**两个同级标题直接相邻。
- **必须**：标题文字不重复（同一父级下）；同名小节必须改名以体现差异。
- **禁止**：标题中出现 Markdown 链接、图片、代码块。
- **禁止**：标题以句号结尾；**禁止**标题只有编号没有文字。
- **建议**：标题写成名词短语或任务短语（「部署流程」「字段映射表」），不写疑问句。
- **建议**：标题层级不超过 4 级（`####`）；超过说明该文档应拆分。

### 5.2 正文骨架

每篇文档按以下顺序组织：

1. `# 文档标题`
2. `> ` 一句话摘要（**必须**，30–80 字，说明结论或用途）
3. 核心结论 / 结论先行段（**建议**，100 字以内）
4. 分节正文
5. `## 相关文档`（**建议**，见第 7 节）

- **必须**：H1 之后的第一块内容是一句 `> ` 摘要，不能是代码块、表格或列表。
- **禁止**：空章节（标题下既没有正文，也没有任何子标题）。
  - **建议**：导航式分组标题（`##` 之下直接挂 `###` 子章节）加一句导语，说明本组的范围与看点；纯分组标题无导语时不构成缺陷。
- **禁止**：占位内容（`TODO`、`待补充`、`xxx`、`...`）留在正式文档中；未写完的文档状态必须为 `草案`。

## 6. 内部链接与交叉引用

### 6.1 写法

- **必须**：指向站内文档的链接使用相对路径，以 `./` 或 `../` 开头。
- **必须**：链接目标必须在同一项目内存在，且归一后不越出项目根。
- **必须**：链接文字描述目标内容，读者不看 URL 也能判断去向。
- **禁止**：裸相对路径（`<category>/<doc>.md`）与裸文件名（`<doc>.md`）。
- **禁止**：以 `/` 开头的项目根相对路径或绝对路径。
- **禁止**：`[[双向链接]]` 语法。
- **禁止**：链接文字使用「点击这里」「点击此处」「本文档」「更多」「详见」「这里」。
- **禁止**：链接到项目外的路径（`../../<other>/...`）。

### 6.2 可达性与一致性

- **必须**：每篇文档至少有一条入链（来自 README 或其他文档）。
- **必须**：改名或移动文档后，全库检索旧路径，全部入链同步更新，断链数为 0。
- **必须**：同一目标在全文中使用同一种链接写法，不混用 `./` 与 `../` 的相对层级错误。
- **建议**：正文首次提到关联概念时给出链接，后续重复提及不再重复链接。
- **建议**：单篇文档内部链接数量控制在 3–12 条；超过 20 条说明主题过宽，应拆分或改为索引页。

## 7. 「相关文档」段

- **必须**：小节标题逐字为 `## 相关文档`，不加编号、不加后缀。
- **必须**：内容为无序列表，每行格式 `- [描述](./<doc>.md)` 或 `- [描述](../<category>/<doc>.md)`。
- **必须**：每条链接的目标存在。
- **必须**：不链接自身，不重复同一目标。
- **禁止**：写成散文、有序列表、表格或代码块。
- **禁止**：包含站外链接、本文内锚点（`#小节`）、图片等非文档目标。
- **建议**：条目数量 3–8 条；按「上位概念 → 平行主题 → 下游应用」排序。
- **建议**：描述控制在 30 字以内，写清「为什么相关」，不写「相关文档」四个字本身。

---

## 8. 单篇篇幅与结构

| 项 | 规则 |
|---|---|
| 主题数 | **必须**：一篇只讲一个主主题；出现第二个可独立成篇的主题时拆分 |
| 正文字数 | **建议**：800–3000 字 |
| 上限 | **必须**：超过 5000 字必须拆分为多篇，并由一篇索引型文档串联 |
| 下限 | **必须**：少于 300 字且无独立价值的文档合并进上位文档，不单独成篇 |
| 段落长度 | **建议**：单段不超过 5 行；超过按语义断段 |
| 列表 | **必须**：单条不用列表；**建议**：并列项 3 条以上才用列表（字段清单、维度清单等两项结构可保留列表） |
| 重复 | **禁止**：同一项目内出现两篇主题重合度高的文档；重复时保留一篇，另一篇改为指向它的短文档或删除 |

结构自检：

- **必须**：读者只读 H1、摘要和各级标题，就能判断这篇文档是否与需求相关。
- **必须**：每篇文档能回答「这是什么、为什么、怎么做、边界在哪」中的至少两项。
- **禁止**：文档末尾出现无信息的「总结」段（复述前文且不增加结论）。

---

## 9. 表格

- **必须**：表格有表头行，且表头下一行是分隔行（`|---|`）。
- **必须**：每行列数与表头一致。
- **必须**：每个单元格只放一个事实或一个判断；需要多个事实时拆行。
- **必须**：数值列在表头写明单位（如「耗时（ms）」「价格（元/月）」）。
- **禁止**：单元格内放图片、代码块、多段落。
- **禁止**：用表格承载超过 8 行的叙述性内容。
- **建议**：列数不超过 6；列数超过 6 时改为「字段清单 + 示例」结构。

---

## 10. 代码块与命令

- **必须**：每个代码块标注语言（```bash、```python、```json 等）。
- **必须**：命令块可直接复制执行，不包含提示符 `$`、`#` 与输出结果。
- **必须**：示例中的密钥、令牌、真实域名、个人路径一律替换为占位符（`<token>`、`<host>`、`<path>`）。
- **禁止**：代码块内出现真实凭据、内部地址、个人信息。
- **禁止**：用截图代替可复制的代码或命令。
- **建议**：单块代码不超过 60 行；超过时只保留关键片段并用注释省略。
- **建议**：代码块前后各有一句说明「这段做什么、预期结果是什么」。

---

## 11. 图片与附件

- **必须**：图片与附件放在项目内的 `assets/` 目录（或分类目录下的 `assets/`），用相对路径引用。
- **必须**：每个图片引用都有替代文本（`![描述](./assets/<asset>)`），描述说明图中内容，不写「图片」「截图」。
- **必须**：附件文件名只含中文、英文、数字、连字符、点，扩展名小写。
- **必须**：图片下方用一行斜体或引用说明「图 N：说明」；图 N 在同一文档内连续编号。
- **禁止**：引用项目外或网络上的图片地址（外部图床、临时链接）。
- **禁止**：图片中承载唯一副本的关键信息；关键信息必须在正文以文字或表格重复一遍。
- **禁止**：图片宽度依赖外部样式；引用时不在 Markdown 中硬编码像素宽高。
- **建议**：单张图片文件不超过 2MB；超过时压缩或拆分。
- **建议**：每篇文档图片不超过 8 张；流程图优先用文字或表格表达结构。

## 12. 更新、废弃与归档标记

### 12.1 状态含义

| 状态 | 判据 | Agent 动作 |
|---|---|---|
| `草案` | 内容未完成或未复核 | 可继续编辑；README 中标注「草案」 |
| `稳定` | 内容完整、可直接引用 | 正常维护；到期复核 |
| `需监控` | 内容可信但依赖会变的外部信息 | 按 `下次复核` 强制复核 |
| `已废弃` | 内容已被替代或失效 | 保留文件，文首加废弃声明 |
| `已归档` | 不再维护，仅作历史参考 | 移入 `archive/`，README 单列归档分组 |

### 12.2 硬性规则

- **必须**：状态变化时同步更新 `最后更新`。
- **必须**：标记 `已废弃` 时，文首（摘要之前）加一行引用块：`> ⚠️ 已废弃：原因；替代文档见 [<替代文档>](./<doc>.md)。`
- **必须**：替代文档链接目标存在；无替代时写「无替代」。
- **必须**：`已废弃` 文档在 README 中保留链接，并标注「已废弃」，不得直接删链接。
- **禁止**：静默删除文档；删除前必须在提交说明中写明原因，并从 README 与全部入链中同步移除。
- **禁止**：把 `已废弃` 文档的内容直接改写为新主题而不更新状态与 `最后更新`。
- **建议**：`已归档` 文档统一移入项目内 `archive/` 目录；归档目录不参与常规导航，但保留可访问路径。
- **建议**：每篇文档超过 `下次复核` 日期后，下一次触碰该文档时必须先复核内容，再更新 `最后更新` 与 `下次复核`。

## 13. 检索友好性

- **必须**：文档标题包含该文档的核心名词；文档存在开篇正文段落时，该名词须在首个正文段落中出现（纯结构化文档——以摘要、表格、代码块、列表为主体而无开篇段落——不适用）。
- **必须**：摘要段（H1 后的 `> ` 行）包含 1–3 个可用于检索的关键词。
- **必须**：同一概念在项目内只用一种叫法；首次出现时在括号内给出别名，如 `限流（rate limiting）`。
- **禁止**：同一项目内用不同标题写同一主题的近似文档（重复内容见第 8 节）。
- **禁止**：标题使用纯代号、纯缩写或无上下文的名词（如「方案 A」「其他」「杂项」）。
- **禁止**：把关键词堆在标题末尾（「……（教程/指南/详解/汇总）」）；一个标题只保留一个定位词。
- **建议**：每个分类目录的名字就是该分类的检索入口词，目录名与 README 小节标题保持一致。
- **建议**：文档中出现的专有名词、命令、配置项保持原文大小写，不做中文化改写。

## 14. 作业流程（Agent 执行顺序）

新增或大幅修改文档时，按以下顺序执行，每步都要能给出判定结果：

1. **定位分类**：确定目标 `<category>/`；不存在则新建，并保证目录名符合第 4 节。
2. **检查重复**：全库检索主题关键词；已有同主题文档时，改为更新该文档，不新建。
3. **起名**：按第 4 节生成文件名；确认同目录无同名、无仅大小写差异的文件。
4. **写元数据**：按第 3 节写 frontmatter；新文档状态一律先写 `草案`。
5. **写正文**：按第 5 节骨架落地；每节写完检查标题层级与空章节。
6. **补链接**：按第 6 节写站内链接；按第 7 节写「相关文档」。
7. **改 README**：在对应分类小节加入或更新该文档链接（**最容易漏的一步**）。
8. **查断链**：逐一验证本次涉及的链接目标存在。
9. **查可达性**：确认新文档能从 README 走到。
10. **定稿**：内容完成后把状态改为 `稳定`，更新 `最后更新` 与 `下次复核`。

## 15. 提交前自检清单

逐项打勾；任一项为「否」即不得交付。

**结构**

- [ ] 项目根只有 `README.md` 一个 Markdown 文件
- [ ] 每个分类目录非空，且不再嵌套子分类
- [ ] 每篇文档只讲一个主主题，字数在 300–5000 之间

**README**

- [ ] 有 H1 与一句话 `> ` 说明
- [ ] 按分类分组，覆盖项目内全部文档
- [ ] 每个链接目标存在，无断链
- [ ] 本次新增/改名/移动的文档已同步更新

**元数据**

- [ ] 普通文档第一行是 `---`，块内有且仅有扁平 `键: 值`
- [ ] `状态`、`最后更新`、`下次复核` 三个键齐全且取值合法
- [ ] `下次复核` 不早于 `最后更新`
- [ ] `README.md` 没有 frontmatter

**命名**

- [ ] 路径只含中文、英文、数字、`-`、`.`、`/`
- [ ] 无空格、下划线、括号、方括号
- [ ] 无以 `.`、`~`、`_` 开头的正式内容文件或目录

**正文**

- [ ] 恰好一个 H1，层级不跳级，无相邻同级标题
- [ ] H1 后紧跟一句 `> ` 摘要
- [ ] 无空章节、无 TODO/占位符（草案除外）
- [ ] 所有代码块有语言标注，无真实凭据

**链接**

- [ ] 站内链接全部以 `./` 或 `../` 开头，目标存在
- [ ] 「相关文档」标题逐字为 `## 相关文档`，且为 bullet 列表
- [ ] 无「点击这里」「详见」这类链接文字
- [ ] 本次改名/移动涉及的旧路径在全库已无残留引用

**生命周期**

- [ ] 状态变更时 `最后更新` 已同步
- [ ] 废弃文档有文首废弃声明与替代链接，README 已标注
- [ ] 无静默删除的文档

**检索**

- [ ] 标题含核心名词，摘要含 1–3 个检索词
- [ ] 同一概念全项目只用一种叫法
- [ ] 无与既有文档高度重复的新文档
