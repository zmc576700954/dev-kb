# 技术决策记录（三）：知识库规范与工程化

> 本文记录知识库规范的落地决策：规范修正、批量提案策略、server 健壮性与范围限定。

## ADR-0019：规范修正以匹配真实文档实践（2026-11-13）

**背景**：kb_spec MCP 在 `ai-video-kb` 上首检报 457 个 error。逐条核对后发现，
其中三类的「违规」实为规范措辞与真实文档实践的错配，而非文档质量问题：

| 规范条目 | 原措辞 | 问题 | 修正 |
|---|---|---|---|
| §5.2 空章节 | 标题下没有任何正文 | 159/159 处是「`##` 直接挂 `###`」的导航式分组，读者可理解结构 | 既无正文又无子标题才算空；导航式分组无导语降为「建议」 |
| §8 列表 | 并列项 3 条以上才用列表；单条不用列表 | 34 处是「输入/参数/审核维度」类字段清单，2 项结构信息更清晰 | 单条=必须；3 条以上=建议（字段清单两项可保留） |
| §4.2 文件名大小写 | 文件名中的英文统一小写 | 12 处全是专有名词（ComfyUI/SDXL/LoRA/TTS…），与 §13「专有名词保持原文大小写」张力 | 补充专有名词例外；校验器只提示纯普通单词 |

**决策**：规范源文件（`web-boke/docs/kb-agent-spec.md`）与 vendor 副本同步修正，
`SPEC_VERSION.json` 记录 sha256 与变更说明；校验器按修正后的语义实现，
规则 ID 保持稳定（`KB-8-list-two` 为新增，承接原 `KB-8-list-min` 的 2 项情形）。

**理由**：规范的价值在于可执行的约束；约束若与领域常识冲突，会诱导 Agent
把优质文档改坏（补 159 句「本节介绍 X」式废话）。修正措辞比迁就文档更可持续。

**代价**：规范文本成为随实践演进的活文档，需要同步 vendor 副本与校验器；
本次共修 3 处。模糊规则（主题重合度、链接文字质量）仍只能产出 review 级发现。

## ADR-0020：批量修复采用「每文档一个合并提案」（2026-11-13）

**背景**：同一文档的多个修复若各生成一个提案，后一个提案的 `before_sha`
基于前一个 apply 前的快照，apply 时报 `stale`（22 个文档批量修复时全部命中）。

**决策**：`scripts/gen_merged_proposals.py` 为每个文档生成**一个**合并提案，
包含 frontmatter 补齐、代码块语言标注、相关文档段补齐等全部格式修复；
`scripts/fix_fences.py` 独立修复围栏配对（早期配对式实现曾把 closing 误标为
新 opening，破坏 15 个文档的围栏结构）。

**理由**：「同一次变更内同步更新 README 链接」（规范 §2.2）与乐观并发模型
要求变更原子化；一个文档一个提案同时满足原子性与可审查性。

**代价**：单提案 diff 较大，需要 `--diff` 视图审查；提案数量从 64 降到 22。

## ADR-0021：MCP server 工具名映射显式化 + 异常不外泄（2026-11-13）

**背景**：把 kb_spec MCP 接入 Claude Code 做端到端验证时，agent 走完
「取 prompt → 生成骨架 → 填内容 → 校验」全流程（errors=0），但在提交提案阶段
收到 `Connection closed`——server 进程已退出。

**根因**（agent 自行发现并报告）：

1. **方法名映射靠前缀猜测**：`_tool_call` 用 `name.startswith("kb_propose_")` 推导
   service 方法名，但 `kb_list_proposals` / `kb_show_proposal` 走的是另一分支，
   实际调用 `getattr(service, "kb_list_proposals")` → `AttributeError`。
2. **异常未捕获**：`except` 只覆盖 `TypeError`/`ValueError`，`AttributeError`
   逃逸到 stdio 主循环 → 进程退出 → 客户端只看到 `Connection closed`，
   真实错误信息丢失。

**决策**：

1. 用显式映射表 `TOOL_METHODS`（工具名 → service 方法名）替代前缀猜测；
   `tests/test_kb_mcp_server.py` 断言映射表与工具定义一致且方法真实存在。
2. `_tool_call` 捕获所有异常，未预期异常转成 `status: error` 结果并附
   traceback 摘要——**server 进程绝不因单次调用失败而退出**。
3. 新增两条回归测试：映射完整性、异常存活。

**理由**：stdio MCP 的进程模型下一个未捕获异常就等于服务不可用，且客户端
拿不到任何诊断信息。「显式映射 + 全捕获」是 stdio server 的基本健壮性要求。

**代价**：新增工具时必须同步 `TOOL_METHODS`——由测试强制，不会漏。

**修复后的第二次验证**：agent 完整走通「取 prompt → 生成骨架 → 填内容 →
校验 → 提交提案」，产出提案 #241（`03-工作流/05-ComfyUI视频化工作流的参数调优.md`，
133 行实质内容），校验 0 errors / 0 warnings / 0 reviews，停在 pending 待人工审批。
人工审查该提案时发现了 ADR-0022 记录的问题（README 未标注草案状态）。

## ADR-0022：提案的 README 变更同样受校验约束（2026-11-13）

**背景**：接入验证的第二次运行中，agent 用 MCP 生成了提案 #241（新建文档 +
README 同步），校验显示 0 errors。但人工审查发现提案里的 README 条目
**缺少「（草案）」标注**——新建文档状态是 `草案`，规范 §12.1 要求 README 标注。
apply 后必然引入一个 `KB-12.1-readme-status-mark` error。

**根因**：`propose_update` / `propose_create` 只校验**目标文档**，
生成的 README op 从未进入校验；而 `_readme_entry_line` 本身也不带状态标注
（带标注的逻辑只存在于 `scripts/rewrite_readme.py`，自动同步路径漏了）。

**决策**：

1. `_readme_entry_line` 增加 `status` 参数：草案/已废弃按 §12.1 标注，
   稳定/需监控不标注（需监控是「按期强制复核」而非「未完成」）。
2. 新增 `_validate_readme_op`：提案中的 README 变更必须过 error 级校验，
   不合规则**拒绝提案**。校验同时跑 `check_document`（文档级）与
   `check_project`（项目级——断链、索引覆盖、状态标注只在这里），只取
   README 自身的发现，避免牵连其他文档的既有问题。
3. 校验基于**变更后**的项目状态：write op 的新内容覆盖旧内容、delete op
   移除路径——否则文档状态已变而校验仍用旧值会误报。
4. `plan_update` 的 README 同步条件补上「状态变化」：稳定↔草案的标注增删
   也要同步到 README。

**理由**：提案门禁的价值在于「落盘即合规」。若提案能携带未校验的变更，
门禁只是形式——apply 后仍要人工返工。

**代价**：每次写路径变更多一次 README 校验（项目级检查，成本可忽略）。

## ADR-0023：kb_cli 批量操作按文档分组执行（2026-11-14）

**背景**：kb_spec 落地过程中产生了 141 个提案，逐个 `approve <id>` + `apply <id>`
不可用。但同一文档的多个提案存在 `before_sha` 依赖——直接按 id 顺序应用，
第二个会因为第一个已落盘而 `stale`。

**决策**：

1. `kb_cli proposals approve|reject <id>... [--project P] [--all] [--dry-run]`：
   按 id / 项目 / 全部批量审批。
2. `kb_cli apply <id>... [--project P] [--all] [--dry-run]`：
   **按目标文档分组**，组内按 id 升序应用。某提案 `stale` 时，该文档的
   剩余提案直接跳过（它们的前置条件已不成立），**其他文档继续处理**。
3. 全部操作支持 `--dry-run` 预览，不产生任何副作用。
4. apply 完成后自动跑一次全库校验并打印 error/warning 计数。
5. `scripts/review_proposals.py` 改为薄封装，批量逻辑统一在 kb_cli——
   避免两套实现分叉。

**理由**：「同一文档的变更必须原子且有序」（ADR-0020 的同一根因）在批量场景下
依然成立：分组执行既保证依赖顺序，又不让一个文档的失败阻塞其他文档。

**代价**：批量 apply 的语义需要用户理解「按文档分组」——通过 `--dry-run`
预览和输出中的分组信息降低误解成本。

**补充（README 增量重放）**：批量场景暴露第二个依赖——多个**跨文档**提案的
README op 都基于同一份旧 README，第一个应用后其余的 README op 必然
`before_sha` 不匹配 → 整批失败。

**决策**：README op 增加 `patch` 字段（`action`/`category`/`target`/`entry`），
记录该提案对 README 的**增量**变更；apply 时若 README 的 `before_sha`
不匹配且 op 带 patch，则在**当前 README** 上重放增量（`_replay_readme_patch`），
而不是用提案生成时的完整内容覆盖。

**理由**：README 是聚合入口，多个文档的条目变更是可交换的独立增量，
用整文件 sha 做前置条件等于把增量变更误当成互斥变更。

**边界**：同文档的多个提案仍会 stale（它们确实互斥——都基于同一份 before），
按 ADR-0023 的分组规则跳过该文档剩余提案。`deprecate`/`archive`/`delete`
的 README op 暂无 patch，批量场景下会 stale（结构性变更批量场景罕见）。

**补充（dry-run 前置条件预检）**：dry-run 若只列提案而不检查前置条件，会给出
误导性预览——历史遗留的 approved 提案可能早已被后续变更取代（实际 apply 时
会因 `before_sha` 不匹配被拒，但预览显示「将应用」）。

**决策**：dry-run 模拟 apply 的前置条件检查，对每个提案标注「⚠ 将 stale：
<路径>（内容已变）」，并在末尾汇总 stale 数量与处置建议（驳回它们）。

**理由**：审批发生在 agent 循环之外，人工看到的预览必须与实际执行结果一致，
否则审批者会对一个注定失败的提案做决策。

## ADR-0024：kb_paths 限定知识库内容范围（2026-11-14）

**背景**：把 dev-kb 自身接入规范校验时发现——它不是「纯知识库」而是**代码仓库兼
知识库**：根目录有 `CHANGELOG.md`（违反「项目根只允许 README.md 一个 Markdown
文件」），`src/agent_app/kb_spec/spec/` 下有 vendor 的规范副本，`reports/` 下有
自动生成的扫描报告。这些都不是知识库内容，但规范的「项目」假设要求全部合规。

**决策**：`kb_projects.yaml` 增加可选的 `kb_paths`（顶层目录白名单）：

- 未配置 → 项目内所有 `.md` 都纳入校验（原行为，向后兼容）
- 配置后 → 只有这些目录下的文档参与校验；**项目根 README 始终参与**
  （它是唯一入口，必须合规）
- 新建文档的路径必须落在范围内，否则提案被拒——否则会建出不被校验覆盖的文档

dev-kb 注册为 `kb_paths: [docs, evals]`。

**理由**：规范假设「项目 = 知识库」，但现实中大量项目是仓库 + 知识库混合。
工具要适应真实场景，而不是逼用户把 vendor 副本、构建产物都改造成合规文档。
范围限定是**声明知识边界**，比让用户做无意义的整改更诚实。

**代价**：范围外的文档不受校验（需用户自行保证）；`kb_paths` 是**顶层目录**
粒度，不能排除某个目录下的个别文件（`docs/` 下的历史归档需靠 `_` 前缀目录
或 `archive/` 约定排除）。
