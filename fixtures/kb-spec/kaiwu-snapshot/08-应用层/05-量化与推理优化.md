# 量化与推理优化

> **当前口径（v9，2026-11-05，dev 120、语料 60）**：默认抽取模型为 Qwen3-4B-Instruct-2507 MLX 4-bit，两遍生成（主抽取 + 定向字段重写），全字段 0.833、结构字段 0.867、JSON 1.000、平均 2.2 s/条。来源：`evals/results/regression/eval-mlx-v4-pp-dev-regression-20261105-003613.json`。
> **历史口径（2026-11-03 模型切换后，dev 120、语料 60）**：同一 4B MLX 4-bit 在单遍生成下为全字段 0.542、结构字段 0.617、JSON 1.000、平均 1.4 s/条（枚举白名单似然裁决）。这是历史，已废弃，不代表当前水平，也不能与 v9 的 0.833/0.867 直接相减。它与 0.5B 的 0.267 是**不同模型**，不是量化带来的差异；0.5B 的量化结论（下方 week8 段）仍成立，但只作为该模型的历史对比。来源：`evals/results/regression/eval-mlx-v4-pp-dev-regression-20261103-220042.json`。
> **历史口径（week8，0.5B，dev 120、语料 60）**：MLX 4-bit + 约束相对 bf16 + outlines，全字段 0.292 对 0.267（+2.5pp，p=0.690）、结构字段 0.350 对 0.333（+1.7pp，p=0.845），均低于配对 MDE 0.113 / 0.115，**不能判定谁更准**；JSON 合法率两侧 1.000。工程收益确定：延迟 0.28 s 对 0.58 s、60 token 0.160 s 对 0.613 s、磁盘 276.1 MB 对 953.3 MB。
> **更早口径（week7b，n=40）**：全字段 0.450 对 0.475、结构 0.475 对 0.500，p=1.000；n=40 的 MDE 约 0.231，+0.025 只相当于 1 条 case，同样不能判定。旧 0.450 不能当当前模型水平，也不能与 0.267 或 0.542 直接比较。

## 目的与口径

目标是让"算法优化"的代价与收益可见，而不是只看速度。两组都用同一 raw 管线：v4 提示词、greedy 解码、max_new_tokens=200、一次修复重试、后处理，不启用 outlines，因为 MLX 侧没有等价的约束解码。bf16 + outlines 的历史默认口径单列一行，避免把两种口径混在一起比较（2026-11-03 起默认已改为 4B MLX 4-bit，见文首）。

计时方法：首 token 为生成 1 个新 token 的耗时（含 prefill），60 token 为生成 60 个新 token 的总耗时，各跑 3 次取中位数。两个后端各起独立进程，避免内存统计互相污染。

**样本量**：原始 raw 对比在 dev 40；能力对齐对比先做 dev 40（week7b），week8 扩到 dev 120。三组数字不能混用。

## 转换与依赖

- 转换命令：`python -m mlx_lm.convert --hf-path models/Qwen2.5-0.5B-Instruct --mlx-path models/Qwen2.5-0.5B-Instruct-mlx-4bit -q`。
- 转换报告 4.502 bits/weight，group size 64，产物 276.1 MB。
- 项目 `.venv` 新增 `mlx-lm 0.32.2`、`mlx 0.32.4`；只安装 Python 包，没有下载新模型。brew 另有 `mlx 0.32.3`（python@3.14），本项目未使用。
- 复现：`evals/quant_bench.py --backend hf --tag bf16-raw` 与 `--backend mlx --tag mlx4bit`，结果在 `evals/results/quant-*.json`。

## 内存口径说明

这些数字是三种统计口径，不能相加、不能互相替换、也不能跨口径做百分比：

| 口径 | 统计对象 | week7b（dev 40） | week8（dev 120） |
|---|---|---|---|
| MPS `driver_allocated_memory` | 框架向 Metal 驱动申请的显存 | bf16 1040.5 MB | 未单列 |
| MPS `current_allocated_memory`（常驻 / 峰值） | 框架已分配张量 | 未单列 | bf16 960.1 MB |
| MLX `get_active_memory`（常驻） | MLX 当前活跃内存 | 未单列 | MLX 268.1 MB |
| MLX `get_peak_memory`（峰值） | MLX 分配器峰值 | MLX 794.2 MB | MLX 794.2 MB（生成后峰值） |
| 进程 RSS 峰值 | 整个 Python 进程（含 Metal 缓冲、统一内存） | bf16 585.0 MB；MLX 807.7 MB | bf16 749.5 MB；MLX 809.3 MB |

因此“框架内存峰值 -24%”是拿 MPS driver 对 MLX peak，属于跨口径比较，只能当量级参考；同口径 RSS 在两周都是 MLX 略高。写报告时必须注明用的是哪一个字段。来源：`evals/results/quant-*.json`、`evals/week8-report.md`。

## GGUF 路径核查

本机有 brew 安装的 llama.cpp 0.6.0_1，`llama-quantize` 存在，但 `/opt/homebrew` 下找不到 `convert_hf_to_gguf.py`；`llama-quantize` 的帮助明确要求输入 `model-f32.gguf`，不能直接量化 safetensors；`models/` 下也没有现成 GGUF。因此 Q4_K_M 组不可用，原因是缺少 HF 到 GGUF 的转换脚本。证据在 `evals/results/quant-gguf-availability.txt`，没有硬凑结果。

分层看：旧 dev 40 上 bf16 全字段 0.450、结构 0.475；新增 80 条上仅 0.175、0.233。这说明 0.267 的下降主要来自**样本变难**，不是模型退化；两轮之间没有同 case 配对，不能把 0.450→0.267 当“模型变差”的统计结论。`urgency` 是当前最大短板（0.59），失败集中在无明确时限的“尽快/比较着急”被判“高”、“不急/周末再约”被判“中”。来源：`evals/week8-report.md`。

能力等价程度：

- 枚举：结果空间等价（必在枚举内），机制不同；候选裁决是分类，不是在解码期逐步屏蔽非法 token。
- 键名与类型：拼装与 schema 校验保证，结果等价。
- 自由文本：仍需自由生成，**不等价**；约束方案只保证 JSON 合法，不保证文本与 outlines 一致。
- c004、c035 的 issue_type 被裁决成"换货"而 gold 是"维修"，说明枚举裁决会与生成式选择分歧；它只保证合法，不保证同选。

同义词修复：给 `ISSUE_SYNONYMS` 补 `"退票": "退货"` 后，MLX raw 的 JSON 合法率 0.975 → 1.000、issue_type 0.725 → 0.750，其他指标不变；bf16 raw 输出中未出现"退票"，前后不变。约束方案不依赖这张表。

## 结论

- 省（工程收益，确定）：磁盘 953.3 MB → 276.1 MB，60 token 0.6133 s → 0.1603 s（dev 120 口径），加载 2.22 s → 0.48 s；MPS 常驻权重占用 960.1 MB → 268.1 MB。
- 赔（raw 口径，dev 40）：JSON 合法率 -2.5 个百分点，结构字段 -2.5 个百分点，issue_type/urgency/summary 下降。
- 不能判定（同口径）：dev 40 上全字段/结构字段 +0.025（p=1.000，MDE 0.231）；dev 120 上 +0.025 / +0.017（p=0.690 / 0.845，MDE 0.113 / 0.115）。两组都在噪声内，**不能写“MLX 更准”，也不能写“两者等价”**。
- 内存要按口径读：MPS driver、MLX peak、进程 RSS 三者不可相减或互相替换。MLX peak 低于 MPS driver，但同口径 RSS 反而略高（dev 120 为 809.3 MB 对 749.5 MB）。
- 默认建议（2026-11-05 更新）：默认抽取为 **Qwen3-4B-Instruct-2507 MLX 4-bit**（2.1 GB，v9 两遍生成，dev 120 全字段 0.833、平均 2.2 s/条）；0.5B bf16 + outlines 保留为历史对照与回退路径，不再是对外默认。2026-11-03 单遍生成时为 0.542、1.4 s/条（历史，已废弃）。MLX 枚举裁决保证枚举合法，但与 outlines 机制不同，不能宣称等价。
- 量化与模型选择的边界：0.5B 上的“bf16 vs MLX 4-bit 不能判定”只说明该模型的量化代价落在噪声内，不能推广成“所有模型 4-bit 无损”；4B 只测了 MLX 4-bit，没有同模型 bf16 对照，**4B 的量化损失未验证**。
- 要判定 +2.5pp 量级的差异，n=120 的 MDE 仍是 0.11；按粗略估算需要约数千条配对样本，本轮不做。
