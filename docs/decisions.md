## ADR-0025：内部 agent 通过 MCP client 复用规范校验（2026-11-14）

**背景**：kb_spec MCP 之外，dev-kb 自身的 agent（`docs_cli` 的文档维护闭环）也需要
规范校验能力。若在 `agent_app` 里再实现一遍校验逻辑，会出现两套实现漂移。

**决策**：

1. 新增 `tools/mcp_client.py`：手写 stdio JSON-RPC client（零新依赖，与
   `kb_spec.mcp_server` 同一理由）——进程管理、stderr 后台排空、id 匹配请求响应、
   超时、`initialize`/`tools/list`/`tools/call`/`prompts/*`。
2. 新增 `tools/kb_client.py`：kb_spec 的语义封装，并提供 `local_search` 降级路径
   （server 不可用时直接用服务层，不报错）。
3. `proposals/llm_draft.py` 在生成草案后调用 `kb_check()`——若该项目受
   `kb_projects.yaml` 管辖，则对草案做规范校验，把 error 级问题附在草案末尾，
   审批者看提案时即可看到「N 处必须修复」。校验不可用时静默跳过，不阻塞提案生成。

**理由**：内外 agent 用同一套校验逻辑，规范才不会分叉。MCP client 让「一套规范
服务 + 多个客户端」成立，也让 kb_spec 能被其他框架挂载。

**代价**：多一层进程间通信（约 1–2 秒启动）；`kb_check` 在草案路径上引入外部依赖，
用 try/except + 降级路径兜住。

## ADR-0026：知识库规范作为 CI 门禁（2026-11-14）

**决策**：`scripts/ci_kb_check.sh` 对 `kb_projects.yaml` 登记的每个项目跑全库校验，
error > 0 退出码非零（阻断合并）；`--strict` 让 warning/review 也阻断，并输出
`reports/kb-todo-<project>.md`。待办清单由 `scripts/todo_report.py` 生成——
按文档分组，含位置、规则、问题与建议动作，同时是 CI 评论与人工整改的共同格式。

**理由**：规范只有进了合并门禁才会持续生效；否则靠人记得检查必然衰减。warning/review
默认不阻断——它们需要人判断，阻断会逼人用「忽略」绕过。

**代价**：CI 需要 Python 环境与 `meta.db`（校验不依赖索引，但 FTS 查重需要）。
