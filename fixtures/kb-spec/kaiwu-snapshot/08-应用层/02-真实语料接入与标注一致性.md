## 目录与格式约定

### 一篇一段政策

真实片段只放 `app/kb_corpus_real/`，一个 Markdown 文件只写一条可独立引用的政策。退货、运费、退款不能塞进同一篇，否则检索只能整篇命中，无法判断引用了哪条规则。

一条工单需要多条依据时，在 gold 标注里组合多个片段，例如 `["REAL-001", "REAL-002", "REAL-007"]`；不要把多条政策合并成一个文件。

### 必备字段与 id

frontmatter 必填 `来源`、`id`、`标题`、`标签` 四项：

- `来源` 固定为 `真实`，导入脚本会校验；
- `id` 形如 `REAL-001`，至少三位数字，与文件名一致，删除后不复用；
- `标题` 建议写成“主题：场景”；
- `标签` 用逗号或顿号分隔，供 BM25 与向量检索使用。

`适用范围`、`版本`、`生效日期`、`审核人` 建议填写；`生效日期` 必须是合法 `YYYY-MM-DD`。

### 与合成语料隔离

- 目录隔离：真实在 `app/kb_corpus_real/`，合成在 `app/kb_corpus/`。
- id 隔离：真实用 `REAL-`，合成用 `KB-`；导入脚本拒绝真实目录里的 `KB-` id。
- 来源隔离：真实片段必须有 `来源: 真实`；合成片段没有该字段。
- 索引隔离：`app/kb_corpus_real/index.json` 固定记录 `"source": "real"`。

## 导入校验

命令：

```bash
.venv/bin/python app/import_real_corpus.py
```

脚本扫描目录内 `*.md`（跳过 README），校验 frontmatter、必填字段、id 格式与唯一性、文件名与 id 是否一致、正文长度、日期格式。全部通过后写出 `app/kb_corpus_real/index.json`，包含 id、标题、标签、适用范围、版本、生效日期、文件 sha256。

- 空目录：打印提示并退出 0，不写索引，不报错。
- 有错误：逐条列出文件与原因，退出 1，不覆盖旧索引。
- 通过：打印片段数与 id 范围。

id 唯一性由“文件名即 id + 文件名唯一”共同保证；脚本同时对 frontmatter id 显式查重。

## 草案占位（不是真实政策）

没有真实政策文件时，用 `app/kb_corpus_draft/` 的 30 条骨架验证导入、检索、模板答案与引用解析。草案只证明链路能跑，不能作为业务依据，也不能代表真实政策效果。

- 主题：与 30 条合成片段一一对应，覆盖退换货期限、运费承担、退款时效、保修范围、投诉升级、发票、价格保护、物流、会员、机票酒店、保险、家政、宽带、智能设备、瑕疵、紧急维修、催办等。
- 标记：frontmatter 固定 `来源: 草案`，id 用 `DRAFT-`；real 模式会拒绝 `DRAFT-` 混入，draft 模式会拒绝 `KB-` 与 `REAL-` 混入。
- 正文：适用范围、触发条件、处置动作、时限、例外情形五节，每条规则都写成 `待确认（示例：...）`，不是确凿条款。
- 导入：`.venv/bin/python app/import_real_corpus.py --mode draft --corpus-dir app/kb_corpus_draft`，30 条通过，索引 `source` 为 `draft`。
- 冒烟：5 条 dev case 用 BM25 + 模板答案全部退出 0，结构化字段、top-3 片段、处置建议、引用与解析引用均有输出。
- 指标：草案没有 gold，不计算 recall、MRR、引用精确率；命中与引用只用于确认链路，不可与合成语料的数字比较。

草案转真实时，必须把 `来源` 改为 `真实`、id 改为 `REAL-`、文件移到 `app/kb_corpus_real/`，并逐项替换 `待确认（示例：...）`。具体清单见仓库根目录 `docs/real-corpus-onboarding.md` 的“待你确认清单”。

## 双人标注与一致性

### 输入格式

工具在 `evals/annotate_kappa.py`。输入两份标注，A 与 B，推荐 JSONL：

```json
{"case_id": "c001", "fields": {"customer_name": "张三", "product": "智能音箱", "issue_type": "退货", "urgency": "高", "order_id": "A20231102001", "summary_text": "智能音箱无法开机要求退货", "evidence": ["KB-002", "KB-006", "KB-007"]}}
```

也支持 `{"items": {...}}`、`{"cases": {"c001": [...]}}`（只有 evidence）和直接 `{case_id: fields}`。标量字段按值比较，缺失记 `<未填>`；`evidence` 按集合比较。

### 输出口径

```bash
.venv/bin/python evals/annotate_kappa.py --a A.jsonl --b B.jsonl --json-out kappa.json
```

输出包含：

- 概览：A/B 条数、共同条目、只在一侧出现的 case；
- 逐字段 Cohen's kappa：标量字段逐一计算，`evidence` 另给“集合完全一致”kappa 与“逐 id 二元 macro”kappa；
- 混淆矩阵：低基数字段给完整矩阵，高基数文本字段给一致/不一致汇总，`evidence` 给逐 id 的 A 有 B 无 / A 无 B 有；
- 不一致条目清单：case、字段、A 值、B 值。

kappa 只作描述性指标，不设硬阈值；先看不一致条目，再判断是口径不清还是个案歧义。逐 id kappa 在 support 很小时方差很大，只作参考；真实标注应保证每个片段有足够的正负样本，或只报告集合级指标。

### 伪 B 演示

用现有单人 gold 生成一份伪 B，跑通链路：

```bash
.venv/bin/python evals/annotate_kappa.py \
  --a evals/annotations/dev40_A.jsonl \
  --b evals/annotations/dev40_B_pseudo.jsonl \
  --make-pseudo-b --seed 7
```

伪 B 由 A 做 7 处固定扰动：2 处 urgency 翻转、2 处 issue_type 改写、2 处删除一个 evidence、1 处 summary 追加“（复核）”。演示结果：

| 字段 | 一致率 | kappa |
|---|---|---|
| customer_name | 1.000 | 1.000 |
| product | 1.000 | 1.000 |
| issue_type | 0.950 | 0.940 |
| urgency | 0.950 | 0.923 |
| order_id | 1.000 | 1.000 |
| summary_text | 0.975 | 0.974 |
| evidence（集合完全一致） | 0.950 | 0.948 |
| evidence（逐 id 二元 macro） | — | 0.953 |

这些数字只验证工具能算，**不是真实双人一致性**。伪 B 的扰动幅度由脚本决定，kappa 高低不反映标注质量，不能写进业务结论。真实一致性必须由第二位标注者独立完成同一批 case 后再跑。

## 接入后要重跑什么

真实语料与真实 gold 到位后，以下指标必须重跑，旧数字不能沿用：

1. 检索：recall@1、recall@3、MRR、主 gold 排第一、top1 非 gold。
2. 引用：引用精确率、引用召回率、主引用命中、引用集合完全相等。
3. grounding：答案是否只使用检索片段；数字型政策是否出现在片段中。
4. 高风险失败：top1 非 gold 但答案看似合理、引用非 gold 但看似合理。
5. 结构化抽取：真实工单字段分布变化时，issue_type、urgency、order_id 等字段准确率重跑。
6. 测试口径：真实 gold 稳定前 test2 继续封存，不用真实 dev 结果替代封存测试。

重跑前还需要真实工单 case 与片段级 gold；否则 `app/evaluate_rag.py` 仍只读合成 dev40。

## 遗留与风险

- 没有真实政策片段、真实工单、第二位标注者，当前无法计算任何真实一致性。
- 合成语料的 recall@3 已饱和到 1.000，不能用来估计真实库上的检索上限。
- 真实政策常有跨片段依赖（主条款 + 例外 + 时效），拆片段时容易拆得过细或过粗；拆法本身需要业务确认。
- 政策会更新；版本与生效日期必须写进 frontmatter，否则旧 gold 会悄悄失效。
