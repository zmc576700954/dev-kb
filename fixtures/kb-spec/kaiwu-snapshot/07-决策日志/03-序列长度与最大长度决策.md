# 序列长度与最大长度决策

> 2026-11-02 决定把 LoRA 训练的 max_len 定为 768，因为 v4 提示词本身约 654 tokens，候选值 640 下 142 条样本全部超长。

## 背景

v4 的 system 提示词、3 组 few-shot 与待抽取原文合计后，prompt 平均 653.7 tokens，target 平均 44.4 tokens，总长度分布为 675 至 718，mean 698.2。序列长度决定了保留多少 few-shot 以及显存占用，是训练前必须定的参数。

## 备选方案

| 方案 | 结果 | 取舍 |
|---|---|---|
| max_len 512 | 142/142 全部超长 | 直接淘汰 |
| max_len 640 | 142/142 全部超长 | 直接淘汰，prompt 本身已约 654 |
| max_len 768 | 0 条截断 | 采用 |
| max_len 1024 | 预计 0 截断 | 无必要增加显存与计算 |
| 删减 few-shot 以缩短序列 | 未实测 | 需要单独消融，会改变提示词效果，本轮不做 |
| 动态 padding 到批次最长 | 未实测 | batch 1 下没有收益，正式训练可再评估 |

## 决策

采用 768。判据是最长样本 718 tokens，768 留出约 50 tokens 余量，且 142 条零截断；512 与 640 在实测中都不可用，不存在“稍微截断”的折中空间。

## 后果

- `max_len` 定为 768，smoke 与 1 epoch 正式训练共用该值；
- 768 不是长期上限：若后续加 few-shot、扩长原文或改 summary 目标，需要重新统计并及时上调；
- few-shot 的 token 成本被固定下来，若未来要做提示词压缩，必须先做消融再改 max_len；
- smoke 在 768 下的显存与耗时只能说明管线可跑通，不能线性外推到正式训练。
