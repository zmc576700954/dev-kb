# 技术决策记录（一）：索引与检索

> 本文记录存储选型、切块策略、混合检索与评测调参的决策，覆盖 M2–M3 与 v3–v6 演进。

## ADR-0001：存储选型 SQLite + Qdrant 本地文件模式（2026-11-12，M2）

**背景**：需要一个存元数据 + 全文索引的库，和一个向量库。

**决策**：SQLite（含 FTS5）做元数据与关键词索引；Qdrant 用本地文件模式（`QdrantClient(path=...)`），探测到 localhost:6333 才切服务模式。

**理由**：
- 单机个人工具，数据量 ~4000 文件 / 十几万块，SQLite 单文件完全够用，零部署、零运维、可单文件备份。
- FTS5 是 SQLite 内置虚拟表，与业务表同事务，块删除时全文索引同步清理，不存在两库一致性问题。
- Qdrant 本地文件模式免 Docker；保留服务模式探测是为未来数据量上来后无缝切换。

**代价**：无并发写（单进程写入足够）；FTS5 分词器弱（见 ADR-0003）。

## ADR-0002：混合检索（符号 ∪ FTS ∪ 向量）+ RRF 合并（2026-11-12，M3）

**背景**：单一检索路都有盲区：向量语义好但认不出精确符号；BM25 认符号但不理解中文语义。

**决策**：五通道召回（符号精确 2.0 / 路径子串 0.6~0.9 / FTS 1.0 / 意图路径提示 0.7 / 向量 0.8），用 Reciprocal Rank Fusion（k=60）合并，不用分数直接相加。

**理由**：各路分数量纲不可比（bm25 rank vs 余弦相似度 vs 通道权重），RRF 只用排名，天然免疫量纲问题，且实现 5 行（`retrieval.py` 的 `add()`）。

**数据依据**：这是 v1 基线（recall@5 0.925）；后续每次修改单通道参数都在 100 题集上验证（见 ADR-0006/0007/0008）。

## ADR-0003：FTS5 中文检索自研 bigram 分词器（2026-11-12，M3）

**背景**：FTS5 默认 unicode61 分词器对中文按"非字母数字"切分，整段中文变成一个超长 token，中文查询直接失效。

**决策**：`fts_tokenizer.py` 把 CJK 字符转二元 bigram，拉丁/数字按词保留；写入索引和查询两侧做**完全相同**的预处理。

**理由**：SQLite FTS5 不支持自定义分词器（除非编译扩展），应用层预处理是唯一免编译方案。bigram 是中文检索的经典取舍：召回高、索引膨胀 ~2 倍但可接受。

**边界**：bigram 无法处理单字查询与同音字；精确符号靠 symbol 列与 LIKE 通道兜底，不依赖 FTS。

## ADR-0004：代码切块用 tree-sitter 按符号切，文档按 Markdown 标题切（2026-11-12，M2）

**背景**：切块质量决定检索上限。按固定行数窗口切会把函数拦腰截断，符号查询命中的是半段代码。

**决策**：
- 代码：tree-sitter 解析 PHP/TS/TSX/Python/Rust，按函数/方法/类/接口/trait 成块，符号限定名带类前缀（`UserController@store`）；模块级代码单独成块；解析失败或无符号时降级 80 行窗口（fallback 标记可见）。
- 文档：markdown-it 解析标题层级，每标题成块并保留 heading_path；>2000 字符按段落二次切，<120 字符的尾部并入前块。

**理由**：符号成块让"canTransition 在哪"这类问题可以走 SQL 精确命中而非模糊语义；限定名前缀解决同名方法冲突。TS 生态里大量"非函数定义"（`const store = {...}` zustand、对象字面量方法），所以额外实现了 `_const_decl_name` / `_pair_function_name` 两个特殊提取器——这是实测五个项目后补的（见 tiangong 的 zustand store）。

**代价**：220 行以上的超大符号按窗口再切，符号内引用跨块时需靠 FTS/向量召回。

## ADR-0005：Qdrant Collection 名携带 Embedding 模型标识（2026-11-12，M2）

**背景**：更换 Embedding 模型时，新旧向量维度/分布不同，混存会导致检索结果不可解释。

**决策**：`COLLECTION = f"chunks_{模型名归一化}"`，换模型自动新建 Collection，旧 Collection 作废重建。

**理由**：把"换模型必须全量重建"从隐性约定变成结构性强制——不同模型的向量物理上不可能混在同一个 Collection。代价是一次重建成本（本机 BGE-M3 全量约十几分钟），换来永不错误复用。

## ADR-0006：Embedding 批次按字符预算而非条数（2026-11-12，M2）

**背景**：BGE-M3 在 Apple MPS 上跑，长文本注意力显存随长度平方增长；64 条短文本一批毫无压力，但 64 条长文本一批必 OOM。

**决策**：预算制分批——每批总字符 ≤ 48k 且 ≤ 64 条，超长块单条成批；入库前按 `LENGTH(content)` 排序取出，让同批长度接近，减少 padding 浪费。

**理由**：OOM 是实测踩坑后的修复（embedder.py 注释）。按长度排序再分批是 Embedding 批处理的通用优化：同一批内长度方差小，padding 少、吞吐高。

## ADR-0007：重排（reranker）只作辅助信号，blend ≤ 0.3（2026-11-12，实验驱动）

**背景**：融合排序后引入 bge-reranker-v2-m3 交叉编码器精排，直觉是"重排分更准"。

**实验数据**（100 题集，对比 baseline-v1）：

| 配置 | recall@1 | recall@5 | McNemar p | 结论 |
|---|---|---|---|---|
| blend 1.0（纯重排） | 0.525 | 0.825 | 0.016 | ❌ 显著退化 |
| blend 0.7 | 0.700 | 0.975 | — | ❌ 仍退化 |
| blend 0.5 | 0.725 | 1.000 | — | △ 持平 |
| blend 0.3 | 0.750 | 1.000 | — | ✅ 采纳（semantic r@1 0.65→0.71） |

**决策**：blend 固定 0.3，融合分主导、重排分辅助；两路分数先各自归一（融合分按最大值归一，重排分经 sigmoid）再加权。

**理由**：交叉编码器对"符号/路径精确匹配"不敏感——查询里的函数名在交叉编码器眼里只是普通文本，而这对 literal 类题恰恰是决定性的。教训写入评审规范：**精确符号通道必须保留主导权**。

## ADR-0008：意图感知加权与评测驱动的参数调整（2026-11-12，v3→v6）

一组小决策，共同点是**全部由 100 题评测集驱动，零显著退化才采纳**：

1. **测试文件降权 ×0.4**（retrieval.py `_TEST_PATH`）：定位生产代码时测试不应排在前面。实现为后处理乘法而非通道排除，保留测试代码被直接询问时的可达性。
2. **路径提示通道（v3→v4）**：中文问法"状态管理"与英文目录 `store/` 之间没有天然映射，扩充 `_PATH_HINTS` 12 项中文→英文目录映射（状态管理/存储/鉴权/组件/接口等）。cross 类 r@5 0.82→0.91，零退化 → 采纳 v4。
3. **路径提示参数（拒绝项）**：权重 1.0/候选 5 条修复 1 题但恶化 4 题（p=0.69）→ **拒绝**，维持 0.7/3。记录拒绝项同样重要。
4. **意图感知代码/文档加权（v5）**：`_CODE_SEEK` 正则识别"在哪/哪个文件/怎么实现"类问题且非文档意图时 code×1.5 / doc×0.7。literal r@1 达 1.00；q029 退化（目标排第 6）但净收益为正、p=1.0 → 采纳。正则而非分类器：规则可解释、零成本、评测可验证，引入 ML 分类器是过度设计。
5. **LLM 查询扩展（v6，三档权重）**：中文问题与英文符号间有词汇鸿沟（"校验文件名" vs `validate_entry_filename`）。用本地 Qwen3-4B 生成 3 个英文候选，整词精确 1.2 / 路径 0.9 / **子词子串 0.3、limit 2**。子词通道（`validate` 挂接 `validate_file`）初版 0.5 权重引入 map-migration 噪音恶化 q029/q061，降到 0.3/2 后修复且零退化。
6. **扩展仅代码定位意图触发**：初版全量触发把文档题 q094 带偏（"文档题被 CUDA/GPU 带偏"）→ 改为 `_CODE_SEEK` 门控。

**方法论**（写入 evals/README 调参流程）：改参数 → 跑一轮 → compare.py 对比基线 → recall@5 不允许显著退化（p<0.05 且恶化）→ recall@1/MRR 提升即收益 → 冻结新基线。

## ADR-0009：LLM 查询扩展结果按问题磁盘缓存（2026-11-12，v6）

**决策**：`data/query_expansion_cache.json` 以问题文本为 key 缓存扩展结果；评测用 `pregen_expansions.py` 离线预生成。

**理由**：本地 4B 模型一次扩展数秒，问答路径上不能每次都跑；缓存让评测可复现、可断点（HF_HUB_OFFLINE 离线模式）。代价是问题改写后缓存失效——当前规模下可接受。

## ADR-0010：回答层实时读取原文件，不用索引副本（2026-11-12，M3）

**决策**：证据包生成时调用 `read_source()` 按行号重读项目文件；文件在索引后发生变化时输出 stale 提示；索引读不到时回退索引副本并明示。

**理由**：索引必然滞后于工作区（未提交改动、外部编辑器修改）。如果 LLM 引用的是索引里的旧代码，用户按行号去核会错位——**可复核性是这个项目的立身之本**，一次"行号对不上"就足以摧毁信任。成本只是多读一次文件。
